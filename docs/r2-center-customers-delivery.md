# R2 客户中心访问层

2026-10-12，用户批准推进并完成本机节点。工作区版本0.17.0-alpha.1，未提交或发布。

## 已批准范围与决定

客户、联系人、来源、归属和手工跟进以现有中心 PostgreSQL 为真源；同一桌面客户端共用业务逻辑，客户界面保留联系人／看板／公司三视图。账号凭据继续由主进程唯一会话适配器持有，页面不另建登录态或数据库连接。

Ruling：复用 M2 的 crm_customers、contacts、companies、共享活动及事务 outbox，而不是新建平行客户库。匿名旧 SQLite 不自动归属、不上传、不删除；正式迁移需另行确认数据归属。R2 不迁移邮箱、发送队列、AI 会话或后台邮件任务，不把这些模块称作中心化完成。

Ruling：沿用旧全局邮箱唯一约束，遇到已有邮箱或来源编号的跨归属碰撞返回安全冲突，不泄露他人记录、不自动合并。代价是不同销售暂不能各自建同一个邮箱的独立客户；后续需显式客户关系／去重规则节点，不能靠取消唯一约束草率处理。

运营读取本人创建来源的客户与其跟进；销售读取本人负责的自有与运营来源客户；全量读取需要 CRM admin 角色、允许的数据范围和 leads.read.all 能力，身份中心管理员资格不隐式授予业务数据权限。原发布／公共池／领取链路暂保留在在线协作入口，定向分配与全局消息合入为 R3。

新建、修改、导入、跟进经服务端校验和事务提交；写命令绑定请求摘要、操作者及幂等键，修改携带版本号。修改保留已有联系人 ID 和活动关系；本节点不提供删除已有联系人。重复提交复用结果并重新核对对象权限。中心不可用时客户操作失败，不自动回写 SQLite。

## 链路与接口边界

客户页面 → ONLINE_CHANNELS → 现有 online-crm service／adapter → 中心 CRM HTTP → 纯服务校验 → PostgreSQL 仓储 → 同事务活动／事件 → 返回中心版本 → 页面重新查询。

新增仅 online:customer-create 和 online:customer-update 两个 IPC，对应 POST /api/crm/leads 与 POST /api/crm/leads/:id/update。列表、详情、文件预览、导入、跟进复用原通道；旧个人 IPC 未改为中心代理，不对旧数字 ID 自动映射 UUID。

## 用户验收入口

重开开发程序并登录，默认进入客户。销售选择自有线索，新建一位客户、记录跟进，再切换联系人／公司／看板检查同一条记录。导入CSV/XLSX查看映射及逐行结果。另一个销售登录后不应看到它；同账号另一窗口应在刷新或五秒轮询后看到。权限按钮需同时有能力和数据范围，现有明确能力子集不会在升级时偷偷扩大；运营／管理账号缺新能力时通过已有管理授权设置核对。

本节点联系人表为每客户首位联系人摘要，其余联系人在详情；既有联系人的删除、原导出／标签／批量发送等未全部迁移。全局邮箱唯一仍会让跨客户相同邮箱发生安全冲突。纯admin通知准入仍有既存限制，不宣称管理员消息完整可用。定向分配、全局消息和在线协作入口整合是R3，持续邮箱／任务为R4，按各节点报告和批准推进。
