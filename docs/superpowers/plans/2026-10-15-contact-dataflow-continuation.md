# 联系人数据链路连续推进计划

> 执行方式：范围确认后使用 superpowers:executing-plans 按节点实施。每节点先保留 checkpoint、完成验证，再进入下一节点；未批准的后续阶段不得自动执行。

**Goal:** 保留现有前端，把联系人详情、已确认修改、跟进记录与邮件关联统一到同一账号授权数据链路，交付可追溯的数据库字段说明。

**Architecture:** PostgreSQL 是已确认业务数据的权威；账号隔离的 SQLite 是本地工作数据。复用当前联系人、详情、修改、跟进和收件箱契约，通过内部数据端口衔接；不把中心数字 ID 当成旧 SQLite 联系人外键。

**Tech Stack:** 当前 Electron、TypeScript、PostgreSQL、better-sqlite3、Vitest；不新增依赖。

**Spec:** 本文件的业务范围与验收；源契约为 server/core/contact-assignments.ts、server/core/center-contacts.ts、src/main/core/contact-mirror.ts、src/shared/online-crm.ts；现状依据 docs/local-contact-read-delivery-20261015.md、docs/mail-dataflow-delivery-20261014.md。

- 保留现有界面布局、样式、导航及交互；必要的错误/数据可用性提示仅使用现有反馈位置，不增加教学文案。

## N1：详情读取统一

原因：列表有结构化本地数据，详情仍依赖独立请求缓存；离线时可能列表可见却打不开，或字段新旧不一致。

提升：列表、详情和邮件匹配读取同一个已确认联系人；详情中的公司资料、活动和邮件摘要按需下载并保存。

影响：首次未下载的历史需要联网，不能把未下载伪装为没有历史；不逐个拉取全库邮件历史。正文和附件沿原收件箱，中心仅当前授权摘要。

涉及文件：src/main/services/online-crm.service.ts、src/main/adapters/online-crm.adapter.ts、src/main/core/contact-mirror.ts、src/main/adapters/contact-mirror-store.adapter.ts、src/main/adapters/contact-mail-runtime.adapter.ts；新增纯详情读取服务。仅在现有契约无法表达历史下载状态时补充可选字段；不重设计 CenterContactDetail.tsx。

接口：消费 CenterContactRef { contactId, customerId }；产生 Result<CenterContactDetail>。复用 online:contact-detail 与 GET /api/crm/contacts/:contactId?customerId=...；不能只拿 contactId 绕过客户关联。
