# AI 驱动销售工作流设计

日期：2026-11-17  
状态：设计稿，待实施  
前置检查点：`D:\Agent Basement\checkpoints\pre-ai-20261117T152309Z`

## 1. 目标

AI 不新增独立工作区，也不要求用户主动选择“AI 模式”。AI 在后台准备业务对象、推进状态并给出下一步，用户仍通过现有客户、收件箱、待办和发送中心完成工作。

两条主链路共享同一个 Case：

```text
已验证线索
→ 自动准备开发任务
→ 用户确认必要事项
→ 现有发送中心触达
→ 客户回复
→ 识别询盘
→ Navigator 查价
→ 用户确认或主管审核报价
→ 现有发送入口回复
→ 成交/流失反馈
```

## 2. 复用现有能力

| 能力 | 现有模块 | 适配方式 |
|---|---|---|
| 多轮开发任务 | `CampaignWizard`、`CampaignTasks`、`campaign.service.ts` | 继续作为唯一批量发信通道 |
| 模板/系统句库/自适应内容 | 现有 Campaign touch mode | 不新增用户可见 AI 模式 |
| 回复、退信、退订止损 | `onContactSignal` 和 Campaign target 状态 | 询盘、正向回复触发后续触达停止 |
| 联系人/邮件聚合 | 收件箱联系人视图和 CRM 联系人 | 注入 Case 状态、询盘和报价草稿 |
| AI 代理 | 中心 AI 管理及代理 | 只生成建议、摘要和分类，不直接发信 |
| 团队协作 | 团队消息、主管、任务 | 报价审核复用团队消息/任务 |
| 运价查询 | Navigator 查询接口 | 结构化查询，不在前端拼价格 |

不新增 AI 发信服务、AI 队列、AI 导航或 AI 工作区。

## 3. 核心业务对象

### `crm_sales_cases`

一个联系人/线程上的销售 Case：

- `case_id`
- `customer_id`
- `contact_id`
- `owner_user_id`
- `state`
- `source`
- `verified_at`
- `latest_message_key`
- `latest_summary`
- `next_action`
- `next_action_at`
- `stop_reason`
- `created_at`
- `updated_at`

### `crm_case_events`

不可变事件账本：

- lead verified
- campaign proposed/approved/started
- mail sent/accepted
- reply/bounce/unsubscribe
- inquiry detected
- quote requested/confirmed/rejected
- user edited/rejected suggestion
- case paused/won/lost

### `crm_ai_proposals`

保存 AI 内部建议，不直接展示为聊天：

- proposal type
- target case/contact
- evidence
- summary
- proposed action
- confidence
- model/policy version
- accepted/ignored/edited by user

### `crm_quote_cases`

- source message/thread
- inquiry fields
- missing fields
- Navigator query runs
- selected quote
- status

### `crm_quote_drafts` / `crm_quote_revisions`

- 报价内容快照
- 选择的运价和备选
- 用户修改
- 版本和发送状态

### AI 成交状态与撤销

AI 从客户来信中识别到合同已签、订单/订舱已确认、客户明确要求按报价执行等成交特征时，默认先把客户标为“AI 已记录成交”，再提示用户确认。该状态不能只做成容易关闭的 toast，必须进入消息中心或客户详情的常驻提示，用户只有选择“取消记录”才会撤销。

落库采用独立、可回滚的 AI 成交事实，不直接把历史中已经关闭的商机临时改成 `closed_won`：

- 有唯一匹配的开放商机，且金额、币种、证据已经齐全时，可在同一事务中推进该商机为 `closed_won`，同时保存上一阶段和字段快照用于撤销。
- 没有唯一商机，或缺少金额、币种时，只记录“AI 已记录成交（待确认）”，提示补全商机；不得猜金额、币种、合同号或订单号。
- 用户取消后，恢复原客户/商机状态并追加审计；已经发生的邮件、活动和证据不删除。
- AI 成交状态先生效，但跨范围成交通知和最终业绩统计只能在成交证据满足现有规则后生成，不能由模型推断替代。

## 4. Case 状态机

```text
lead_pending
→ lead_verified
→ outreach_ready
→ outreach_running
→ awaiting_reply
→ replied
→ inquiry_detected
→ fields_pending / quote_ready
→ quote_review
→ quote_sent
→ negotiating
→ won / lost / paused
```

硬规则：

- 未验证线索不得进入自动触达。
- 收到正向回复后 Campaign 必须停止。
- 退信、退订、投诉必须停止。
- 询盘不得继续走批量开发内容。
- 报价必须经过用户确认；是否需主管确认由金额、航线或团队策略决定。

## 5. 冷开发自动准备

### 5.1 导入后

1. 本地规则先完成格式、重复、禁用联系人、退订、归属和基础资料校验。
2. 必要时 AI 判断公司/业务相关性，但只生成通过/待确认/不通过建议。
3. 通过后自动创建一个 Campaign 草稿，不直接运行。
4. 用户进入发送中心时，草稿已经带有联系人、建议分组、触达轮次、账号和内容。

### 5.2 必须人工确认

- 邮箱/域名可疑
- 联系人与公司不匹配
- 客户归属冲突
- 已有开放商机或近期已联系
- 发信账号不可用
- 基础模板缺变量
- 客户禁止联系或退订
- AI 建议置信度低

界面使用正常业务提示：“需确认 3 项后开始”，不显示 AI 模式。

### 5.3 分群与分配

AI 按以下维度聚合，不为每条线索单独建任务：

- owner/team
- 国家、语言
- 客户类型
- 航线/港口/货种
- 新客户/沉默客户
- 可用发信账号和健康度
- 发送容量

账号分配约束：

- 团队归属优先于负载均衡
- 同一发送账号保持业务一致性
- 新账号必须低速预热
- 退信和限流异常账号停止分派

### 5.4 发信速率硬约束

限流由发送服务执行，不由 AI 自行遵守：

- 全局硬上限：180 封/小时
- 软目标：120—150 封/小时
- 突发上限：10 封/分钟
- 单账号独立上限
- 单收件域独立上限
- 发送间隔 15—40 秒随机抖动
- `421/450/451/454` 自动降速
- 退信/投诉/限流率达到阈值时暂停队列

队列领取任务和真实 SMTP 前都要复核限流。

### 5.5 内容策略

- 同一客群共享基础内容，再按联系人变量生成。
- 不逐封调用模型。
- 高价值/上下文特殊客户才单独生成。
- 已回复客户不再生成下一轮。
- 用户编辑后的内容进入反馈账本。

## 6. 询盘与报价

### 6.1 后台触发

邮件入站后自动执行：

```text
是否客户业务邮件
→ 是否询盘
→ 字段抽取
→ 主数据解析
→ 缺失字段判断
→ Navigator 查询
→ 报价草稿
```

不要求用户点击“分析”。

### 6.2 字段

- POL/POD
- 柜型和数量
- 品名、重量
- 船司偏好/排除
- ETD、有效期
- Incoterm
- NOR、冷藏、危险品、超尺寸
- 目标价

每个字段保存原文证据、置信度和用户修改。

### 6.3 报价卡

报价卡是持久 `quote_draft` 的投影，不是临时 UI：

- 推荐运价
- 备选运价
- 船司、ETD、有效期、数据日期
- 缺失/冲突字段
- 用户修改条件
- 重新查询
- 起草回复
- 请求主管确认

打开对应邮件时以右侧浮层/悬浮卡展示；关闭后邮件仍保留“待报价”状态。

### 6.4 主管审核

复用团队消息/任务，不新增通道：

- 发起 QuoteReviewRequest
- 主管查看报价、客户原文和修改历史
- 同意、退回或要求重新查询
- 回写 QuoteRevision

## 7. Logo 动态助手

Logo 是状态提示，不是常驻聊天机器人。

状态：

- 有新事项：轻微动效
- 有风险：稳定警示点
- 无事项：静止

点击显示最多 3 条：

- 今天优先客户
- 待报价询盘
- 即将过期报价
- 异常发信/退信

同一建议不重复提示；用户处理、忽略或延后后消失。

Logo 对话只处理操作型问题：

- 今天先做什么
- 找出待报价询盘
- 为某客户准备回复
- 哪些开发任务将超出限额

## 8. UI 引导

- 不新增 AI 导航和 AI 页面。
- 只有一个“下一步”高亮。
- 高亮通过现有按钮的轻微动效、引导环或旁侧提示实现。
- 用户完成、忽略或切换页面后立即取消。
- 不反复弹教程，不阻塞主界面，不造成布局位移。
- 支持减少动画设置。

## 9. 反馈与学习

隐式反馈：

- 编辑/替换内容
- 修改字段
- 选择不同运价
- 重新查询
- 忽略/延后建议
- 请求主管审核
- 最终发送/放弃
- 客户接受/拒绝

初期只用于规则、模板排序和提示词评估，不直接训练模型。

## 10. 可观测性和安全

- 每次 AI 调用有 request id、功能、模型、token、耗时和结果。
- 每条 AI 建议保存证据和版本。
- 不保存完整邮件正文到中心 AI 用量表。
- 港口、船司、柜型、价格不得由模型凭空补全。
- 外部发送、报价发送和主管审批保留明确权限检查。
- AI 不可自行提高发送限额或绕过 Campaign 确认。

## 11. 实施阶段

### 阶段 A：Case 与事件底座

- 新增 Case/Event/Proposal 契约和中心表。
- 导入验证、回复事件、询盘事件接入。
- 不改变现有 UI 操作方式。

### 阶段 B：开发任务自动准备

- 导入后创建 Campaign 草稿。
- 增加必要确认项。
- 加入全局/账号/域名限流。
- 回复信号停止后续触达。

### 阶段 C：询盘报价卡

- 字段抽取和主数据解析。
- Navigator 查询适配。
- QuoteDraft/Revision 和邮件侧浮层。
- 主管审核复用团队消息/任务。

### 阶段 D：Logo 助手和引导

- 每日简报和待处理提示。
- 现有按钮的单步引导特效。
- 隐式反馈采集。

### 阶段 E：策略优化

- 根据回复率、询盘率、字段修正率和报价采用率调整策略。
- 达到样本门槛后再评估小模型微调。

## 12. 验收标准

- 导入 200 个已验证线索只生成少量任务草稿，不生成 200 个独立任务。
- 全局任一小时发送不超过 180 封，突发不超过 10 封/分钟。
- 客户回复后，后续 Campaign 触达在下一发送检查点停止。
- 询盘邮件无需用户点击分析即可出现报价卡。
- 报价卡关闭后仍可从邮件/联系人恢复。
- 用户修改字段会重新查询并保留版本。
- 主管审核通过后，报价可进入现有发送入口。
- Logo 无事项时静止，最多同时提示 3 条。
- AI 不可绕过发送、报价和主管审批权限。
