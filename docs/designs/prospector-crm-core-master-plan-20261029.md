## 目标

在不改变现有 Electron、React、Ant Design、PostgreSQL、core/services/transport 分层和客户页交互核心的前提下，完成组织、分配、归属冲突、邮件分析、主管监督和运营监控闭环。

本计划优先建立稳定体系和权限边界。销售指标和客户 A/B/C 分级按 CP7 实时派生，人工等级覆盖单独留痕；不保存评分快照，不把评分自动变成分配垄断权重。

## 冻结的不变量

- 销售之间默认不可见，不得通过搜索、导出、团队目录或共同编辑绕过。
- 联系人只归属具体销售，团队永远不是联系人所有者。
- 所有运营管理员共享运营线索池，不以运营组做账号间鉴权隔离。
- 运营组只用于组织、来源、筛选和批量分配。
- 主管是团队关系角色，同时也是销售；不新增全局 CRM 主管角色。
- 一个普通销售最多归属一个叶子团队；一个主管可以负责多个团队。
- 每个团队只有一个主要负责人；多个超级管理员共享公司根，不各建根团队。
- 分给主管的线索不自动向团队成员共享；分给成员的线索自动通知直属主管并获得监督可见。
- 普通分配的通知对象由服务端组织关系强制计算，前端不能取消。
- 一个联系人只有一个当前负责人，最多一个 `pending` 或 `accepted` 分配。
- 所有手工、导入、Agent、API、恢复和迁移入口必须经过同一线索入口和冲突检查。
- 模糊公司匹配只能产生候选和人工裁决，不能静默合并。
- 已触达表示我方完成有效动作；已回复只表示客户本人有效回复；自动回复和退信不算回复。
- 完整邮件正文和附件继续本地保存；中心保存元数据、摘要、业务信号和必要关联。
- AI 不得修改负责人、客户归属、成交结果或人工已确认状态。
- 客户页继续是联系人、商机、邮件和客户写操作的唯一入口。
- 沿用现有 Ant Design 主题、`workspace-*` 配色变量、8px 以内卡片圆角和克制布局，不建立第二套设计语言。

## Agent 结构

### 主 Agent

高模型负责：

- 解释并冻结用户决定
- 拆分阶段和文件写集
- 维护主计划、契约和 check.p
- 分派实现任务
- 处理 Agent 之间的冲突
- 运行最终门禁并向用户交付

主 Agent 必须保留完整产品上下文，是唯一可以批准契约变更和扩大范围的节点。

### 实现 Agent

低模型按阶段或互斥写集执行：

- 只接收当前阶段上下文，不读取无关历史讨论。
- 每个 Agent 只能修改指定文件和测试。
- 同一阶段若需要前后端并行，使用不同文件写集或独立工作树。
- 任一关键契约缺失时，不自行定义第二套替代结构。

### 审查 Agent

独立旁路模型负责：

- 越权、隐私、销售互相可见等安全问题
- core/services/transport 分层
- 状态机、幂等、版本、事务和并发
- 是否重复存储可由查询派生的状态
- 是否偏离现有客户页和设计语言
- 测试是否覆盖失败、并发、权限和回滚

Reviewer 不修改业务代码。主 Agent 处理问题后重新提交审查。

### 是否新开用户可见对话

不建议为每个阶段新开用户可见对话。主对话保留最终目标和批准记录，内部使用隔离子 Agent 上下文与独立工作树即可防止污染。

原因：

- 新用户对话会丢失全局决定和批准顺序。
- 多 Agent 真正需要隔离的是实现上下文和文件写集，不是把产品负责人拆散。
- 独立 Reviewer 使用单独上下文即可，不需要单独占用用户对话。

## 分层落点

每个业务阶段遵循同一代码结构：

| 层 | 职责 | 典型目录 |
|---|---|---|
| core | 类型、状态机、权限、纯规则 | `server/core/` |
| services | 用例编排，不碰 IO | `server/services/` |
| adapters | PostgreSQL、SQLite、IMAP、AI 适配 | `server/adapters/`、`src/main/adapters/` |
| transport | HTTP/IPC 路由和输入适配 | `server/transport/`、`src/main/transport/` |
| shared | renderer/main 共用契约 | `src/shared/` |
| renderer | React Query、页面、组件 | `src/renderer/` |

统一返回 `{ ok, data?, error? }`。新增依赖先审批，优先使用现有 Ant Design、React Query、Lucide、PostgreSQL 和 Electron 能力。

### CP2 - 线索归属、分配和自动监督

- 全量权限负向测试和真实 Electron 点击链路。

### CP3 - 统一线索入口与客户防冲突

后端：

### CP4 - 邮件分析、业务信号和任务资格

- 机械规则先判断收发方向、回复、退信、自动回复、线程和联系人关联。

- 使用 `mailboxKey + messageKey + contentHash` 幂等，版本追加，人工修正优先。
- 新增 `crm_contact_mail_analyses` 追加表，保存 source、summary、signals、requiresAction、nextAction、priority、confidence、model/prompt version。
- 只有匹配授权客户的业务邮件更新联系事实。内部、平台、广告、垃圾和未匹配邮件不进入销售指标。
- `requiresAction` 与标签分离；标签只做展示。
- AI 可建议但不能自动修改负责人、客户归属、销售阶段和成交结果。

核心代码：

- `server/core/mail-analysis.ts`：固定分类、结构化信号、任务资格、状态映射。
- `src/main/services/mail-analysis-queue.service.ts`：本地后台队列。
- `server/services/contact-mail-analysis.ts`。
- `server/adapters/postgres/contact-mail-analysis-repository.ts`。
- `src/shared/online-crm.ts` 扩展邮件分析 DTO。
- `InboxList`、联系人详情和主管邮件摘要复用现有页面。

前端：

- 收件箱展示摘要、业务信号和“需要行动”标记。
- 业务信号使用结构化 chip/列表，不无限增加自由标签。
- 人工可修改分类、关闭任务建议和修正联系人关联。
- 未匹配或非客户邮件保持普通收件箱状态，不污染联系事实。

check.p：

- 机械分类与 AI 分类冲突、AI 超时、重复分析、人工修正、退信、自动回复和客户回复测试。
- “已触达/已回复”语义和状态转换测试。
- AI 不修改负责人、阶段、成交和人工确认字段。
- 中心只接收元数据、摘要和信号；正文附件不上传。
