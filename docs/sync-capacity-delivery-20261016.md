# 同步日志维护与容量验证交付

工作区版本：0.50.0-alpha.1；2026-10-16。用户批准的同步维护及容量节点，现有界面保持。没有启动在线营销 Worker、迁移历史 contacts 或操作真实业务数据。

## 改动与数据链路

原问题是同步循环对每一条历史记录反复读取、反序列化全部命令；不仅占空间，还会阻挡真正待提交的修改。现在状态、详情草稿和同步循环只读未解决命令，单条及前驱按索引查询。事务内再次检查幂等键，避免另一个窗口刚确认的记录被覆盖。

```text
原字段/跟进组件 → 原 IPC → 持久化 pending → 原 HTTP → 中心 PG 确认
                                                   ↓
                         本地确认投影 + confirmedAt（真实回执时刻）
                                                   ↓ 满30天且无未解决直接依赖
                         同一行最小 receipt（永久去重凭据）
```

每次原同步入口最多处理100条维护写入；没有新增定时器。遗留记录没有确认时间时，先从首次维护时刻开始完整30天，不能按很早的创建日期立即压缩。pending/conflict/failed保留完整输入；仍被未解决命令直接引用的确认前驱保留。压缩不改变中心业务事实、联系人版本或邮件。

## 数据库结构与字段

中心 PostgreSQL 无迁移、表列或索引变化。本地仍是账号 crm-offline.db 的同一张表，无新增表列：

```text
crm_contact_commands
├─ permission_key TEXT NOT NULL ┐ 联合主键
├─ command_id     TEXT NOT NULL ┘
└─ payload        TEXT NOT NULL  完整命令 或 最小确认凭据
```

完整命令新增可选 `confirmedAt`：ISO时间，中心成功回执实际被安全接收时写入。旧 `createdAt`、input、attempted、predecessorId、error、retiredKeys、history语义不变。

| 最小凭据 payload 字段 | 用途 |
|---|---|
| kind = receipt | 显式区别于仍含输入的命令，避免当作可重发命令 |
| id / action / status=confirmed | 原命令身份、操作类型、确认状态 |
| contactId / customerId | 原中心关联；不能单独用于恢复授权 |
| confirmedAt | 确认时间，保留生命周期依据 |
| inputDigest | 对规范化原请求计算的SHA256；同键不同内容仍拒绝 |
| idempotencyKey | 最终请求键，永久保留重复提交保护 |
| retiredKeys（可选） | 冲突重试前的旧键，不允许被再用 |

压缩后删除本地命令中的 input/history；它不是业务跟进历史的删除，也不影响中心活动或本地邮件。五个新索引均在原表：status、key、retired、predecessor、retention，分别服务未解决状态、当前键、退休键候选、依赖、确认时间范围。DDL唯一来源为 `src/main/adapters/contact-mirror-store.adapter.ts`。首次打开既有数据库自动创建索引，需要扫描旧命令；不修改旧业务表。

维护按确认时间拆成空值/到期两个索引范围；前驱比较移除SQLite TEXT亲和性，确保JSON表达式索引两列均参与检索。已添加查询计划回归。100是维护写入上限，不是固定100次读取预算：大量受保护前驱仍需要线性检查；独立隔离SQLite测试10万确认记录＋10万全部阻塞依赖约100ms。退休键匹配仍随含退休键记录数量增长。

## 容量结果

本机 i5-14400、约16GB内存，实际 Electron 37.10.3 原生磁盘SQLite；每条确认命令约1.65KB。下表使用最终 after3 证据，读取三次采样，写入/补传单次；不是P95或生产并发承诺。补传使用进程内成功回执替身，排除HTTP、中心及SMTP耗时。

| 场景 | 优化前 | 优化后 |
|---|---:|---:|
| 1万确认日志＋500待处理：详情草稿 | 125–164ms | 1.2–2.3ms |
| 同规模：状态读取 | 105–202ms | 1.3–1.4ms |
| 同规模：离线保存 | 850ms | 24ms |
| 同规模：补传50条 | 30秒超时，0条调用 | 148ms，50次调用 |
| 10万确认日志＋5000待处理：详情草稿 | 1.09–2.01秒 | 16–31ms |
| 同规模：状态读取 | 1.98–2.27秒 | 17–20ms |
| 同规模：离线保存 | 12.35秒 | 155ms |
| 同规模：补传50条 | 30秒超时，0条调用 | 527ms，50次调用 |

联系人列表仍完整读取授权快照后筛选：最终10万条采样464–499ms，本轮没有实现索引分页，不宣称它已提速。旧库首次创建五索引实测10万命令约3.6秒，期间同进程可能短暂等待。既有记录缺少确认日期时，单批初始化100条约347ms；到期压缩100条约23ms。并行开发测试可能影响CPU/磁盘采样，不能将前后差异外推到所有设备。

每种规模仅在隔离数据库中人为推进测试时钟并分十批压缩1000条：10万规模payload字符合计减少1,374,000；没有自动VACUUM，不保证操作系统看到的文件立即缩小。最小凭据永久保留，记录数仍随成功修改线性增长；本次解决完整输入积压和历史反复解析，不承诺无限容量。

中心另用一次性真实PostgreSQL＋原服务测量10万联系人、每页50条：第一页282–320ms，末页1.57–1.63秒，搜索约290–304ms。权限范围/页数断言通过并事务回滚，测试实例停止删除。这里未走HTTP，也未模拟多人并发；深分页是后续有证据的优化点。
