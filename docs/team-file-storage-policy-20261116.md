# 团队消息与文件存储策略

## 适用范围

本策略同时覆盖团队私聊附件、聊天记录归档和后续邮件引用/运价快照中的文件对象。团队消息事实仍以中心 PostgreSQL 的 `crm_team_messages` 为准；文件内容不写入消息正文，不把二进制塞进 JSONB 或 IPC 大对象。

## 存储分层

1. `crm_team_messages` 保存消息事实：发送人、接收人、类型、正文/快照、创建时间、幂等键。
2. `crm_team_files` 保存文件元数据：文件 ID、用途、原始文件名、MIME、字节数、SHA-256、创建人、存储后端、相对对象键、创建时间。
3. 文件本体不通过数据库端口传输，也不存进 `bytea`；文件走中心文件服务，消息和文件元数据走中心 PostgreSQL。
4. 聊天记录归档生成独立文件对象，用途为 `team_archive`，不修改原始消息，也不替代数据库事实。

## 最终部署形态

- 桌面客户端只访问中心 HTTP API，不从客户端直连 PostgreSQL，也不持有文件存储凭据。
- 公司服务器上的中心 API 负责鉴权、团队范围校验、文件元数据写入和文件对象读写。
- 首期可以使用公司服务器本地受控目录或挂载盘作为文件后端；最终迁移到 S3/OSS/MinIO 时只替换“中心文件存储适配器”。
- 文件对象键必须是相对键和不可变 ID，不能保存服务器绝对路径；迁移后同一 `fileId`、`sha256` 和元数据仍然有效。
- 建议配置：`PROSPECTOR_FILE_BACKEND=local|s3`、`PROSPECTOR_FILE_ROOT`（本地/挂载盘）、对象存储 endpoint/bucket（后续）。客户端不读取这些配置。

## 文件规则

- 单文件默认上限 8 MiB；超限拒绝并返回明确错误。
- 文件名只作为展示元数据，存储键由服务端生成，不能使用用户提供的路径。
- 允许 MIME 采用白名单；未知或可执行类型拒绝。
- 文件内容按 SHA-256 校验，元数据与文件写入必须保持一致性。
- 删除采用元数据软删除加延迟清理；消息引用仍可审计，不能因清理文件而删除消息。
- API 永不返回真实磁盘路径，只返回 `fileId` 和展示元数据。

## 聊天记录归档

- 归档由用户显式触发，按 `teamId + peerUserId + 时间范围`读取双方私聊。
- 归档内容包含消息 ID、发送人、接收人、类型、正文/快照、时间和已读状态，不包含附件二进制。
- 归档文件属于当前发起用户可见，不扩大对方权限。
- 归档生成后返回文件元数据；下载仍需中心鉴权。

## 备份与迁移

- PostgreSQL 备份覆盖消息、阅读游标、文件元数据和归档索引。
- 文件存储备份覆盖实际对象；恢复时先恢复元数据，再按 `storage_backend + object_key` 恢复对象并校验 SHA-256。
- 从本机开发环境迁移到公司服务器时，按“消息/元数据导出 -> 文件对象复制 -> 校验数量与哈希 -> 切换中心文件后端 -> 回滚演练”执行。
- 不把本机绝对路径、开发凭据或临时目录写入生产消息记录；文件迁移不能改动消息 ID、已读游标或任务邮件关联。

## 资源受限部署的硬约束

当前中心服务器不能按“永久保留全部聊天正文和附件”设计。默认预算按以下顺序控制：

1. 邮件正文/附件仍留在各销售电脑的 IMAP 本地缓存，Prospector 中心只保存 CRM 事实、邮件摘要和团队消息。
2. 团队消息热库只保留最近 30～90 天；更早消息按月压缩为 JSONL/Zstd 归档，数据库只保留归档索引和必要审计字段。
3. 聊天附件只保存元数据；文件本体进入独立文件卷或对象存储，客户端按需下载，不在消息 JSON 中重复保存。
4. 附件按 SHA-256 内容寻址去重；同一文件只存一份，多个消息只引用同一个 `fileId`。
5. 图片保存原图加按需生成的缩略图，不预先为每个文件生成多套尺寸；客户端缓存使用容量上限和 LRU。
6. 设置团队/用户配额和保留期。达到配额时拒绝新附件，并提示清理归档，不允许无限吃满服务器磁盘。
7. 归档文件使用压缩格式；数据库只保留 `fileId、sha256、大小、时间范围、对象键`，不保存归档正文副本。

粗略容量判断：文字消息不是主要成本，附件和归档才是。150 名销售即使每年产生数百万条短消息，压缩后的文本通常仍是百 MB 级；真正需要限额的是图片、PDF、Office 文件和聊天归档。

## 200 人业务交流容量基线

按 200 个有效账号、约 50 个同时在线客户端设计，不按 200 个客户端同时跑全量同步来估算。

- 消息量：按每人每天 100 条、每条平均 400 字节估算，日增约 8 MB 文本，年增约 2.9 GB 原始文本；PostgreSQL 行开销和索引会放大到数倍。90 天热库通常控制在 2～4 GB 量级。
- 归档量：按月压缩 JSONL/Zstd 后，文字归档通常会显著小于热库；保留 180 天时按 5～15 GB 预留即可，具体以真实消息长度和索引策略为准。
- 附件量：这是主要变量。默认每团队每月 200 MiB、每用户每月 50 MiB，超过后拒绝新附件并提示清理；文件保留 30 天，归档附件按团队策略延长。
- 推送连接：200 个账号、50 个同时在线 SSE 连接是可控的；主进程每账号只建一条连接，不能按窗口或页面重复建连。
- 热查询：最近 90 天消息按 `team_id + conversation_seq` 索引查询；旧消息只走归档索引，不参与日常会话列表扫描。
- 本地缓存：每个客户端只完整缓存本人可见会话；默认附件缓存 2 GB，超过按 LRU 清理，客户端 SQLite 设置 WAL 和容量告警。

按这个基线，中心服务器不需要为 200 人预留“微信级”海量空间。真正要严格控制的是：重复附件、长期不清理的图片/PDF、聊天归档无上限增长，以及把邮件正文/附件误传中心。

## 尚未落地

- 当前只有策略和元数据边界，尚未实现上传、下载、附件消息气泡和归档按钮；实现时必须按上述中心 API + 文件适配器边界落地。
- 推送仍保持后续单独立项：主进程单连接、SSE 优先、断线回退可见轮询。
- 本策略不授权正式中心部署；迁移和服务重启统一在维护窗口执行。
