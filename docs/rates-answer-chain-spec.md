# agent 运价反应链与呈现规则（触发 → 两段查 → 表格交付）

日期：2026-09-08　用户定案：**收到任何用户提出的价格/运价等提示，agent 都要首先精准查询、
再按航线查询运价库，并严格生成为表格形式。**

本文件是这条反应链的**唯一口径**，与既有规范的关系：
- `rates-query-fallback-spec.md` 管「查不到时怎么说」（L2 换词重试 / L3 定论）——本文管「查得到时怎么查、怎么给」；
- `rates-query-spec.md` §3/§4 管两张表的字段与占位——本文规定**谁生成、谁不许改**；
- `rates-remote-source-spec.md` 管台账地址来源。

## 1. 触发：只要沾价格就查台账，没有例外

命中任一条即必须调 `quote_search`，**禁止**凭记忆、常识、上一轮的结果或市场估价作答：

- 出现「运价 / 报价 / 价格 / 多少钱 / 什么价 / 报多少 / 低价 / 降价 / 涨价 / 区间 / 成本 / 特价」等词；
- 提到「港名 / 航线名 / 区域（南美东、加勒比、地东…）+ 柜型（20GP/40HQ/40NOR）」的组合；
- 问「库里有没有 / 我们报过多少 / 哪条线便宜 / 哪几家有价」这类统计或比选问题；
- 客户询价邮件要回价（回信链路 `generate_draft` 会自己查，见 `agent-draft-reply-spec.md`）。

反向红线：`market_research` 是「外面报多少」，不是「台账上多少」；两种都要就先台账后市场，
**两边的数字不许混成一句**。「本地镜像查不到」永远不等于「这条线没有报价」。

## 2. 两段查询：工具内部按顺序做，不要求模型猜词

模型只把用户原话里的词传进来（`q`/`pod`/`pol`/`lane`/`container`），**判断"是港还是航线"不是模型的活**。工具按序执行：

| 段 | 查什么 | 命中条件 | 备注 |
|---|---|---|---|
| **L1 精准港** | `resolveQueryPod(词)` 归一成标准港名（别名/LOCODE/中文译名 → `SANTOS`）→ 只筛 `pod_raw` 含该港的行 | 有行即用 | 柜型可筛；起运港**不做硬筛**（`pol` 是中文群名，硬筛会漏掉「华南基本港」这类） |
| **L2 航线级** | L1 为零、或用户明确说整条线/基本港时：用 `podRawExpansion` 取该港所属航线与区域码（`南美东`、`WCSA`…），捞**航线级报价**，POD 展开回目标港 | 表里标注「航线级报价，适用该航线基本港」 | 命中后 `polAligned=false` 时须逐条写明起运港 |
| **L3 定论** | 两段都空 → 走 `rates-query-fallback-spec` 的 candidates 换词重试与「镜像落后真源 / 确实没有」分层口径 | — | 空结果不进读缓存（否则换词重试被缓存挡住） |

> 现状与目标的差距见 §5：现在 L1+L2 被一次跨字段 OR（`terms`）合并掉了，
> 「先精准后航线」的顺序没落地——航线级区域价会和具体港价混排，比选时容易把区域价当成本港价报出去。

## 3. 呈现：表格由工具生成，模型只许原样贴

**三件套，顺序固定，一个都不许多余：**

1. **一句结论**（最低价 / 条数 / 覆盖船司），数字全部照抄工具返回的 `answer`；
2. **工作表**（给操作者自己看）= 工具字段 `userTable`，12 列中文，顺序锁死：
   `船司 · 起运港 · 目的港 · 20GP · 40HQ/HC · 40NOR · 目免 · 有效期 · 备注 · 来源 · 发送人 · 入库时间`
   ——唯一出口 `rates-clean.cleanTableMarkdown`（港口拆分归一、三列柜型价透视、未标注判丢全在里面）。
   **来源/发送人/入库时间必须出现**：这是操作者核对信息出处的三列，不是可选装饰。
3. **舱位动态**（有则给，紧跟其后）：照 `spaceTable` 原样贴，注明以订舱时确认为准。

**客户报价表**（对外交付物）：英文十一列 `CARRIER/POL/POD/20GP/40HQ|HC/40NOR/FT/ETD/VALIDITY/TT/REMARK`，
唯一出口 `rates-clean.customerQuoteMarkdown`（回信侧同源，见 `agent-draft-reply-spec.md`）。
**必须问了、用户点头才出**，不许静默生成。

**模型侧四条禁令**（写进工具 notice 与系统提示词，弱模型对工具返回里的指令最服帖）：

1. 表格是成品，**列名、列序、数值、`/` 占位一个都不许改**，不许合并行、不许补数；
2. 不许把表改写成散文或要点列表，也不许只说「查到了 N 条」让用户自己去翻；
3. 不许另拼第二张表（工具表之外再手写一张 = 双表打架，实测翻车源头）；
4. 表外只允许一句结论 + 参考价提醒（「镜像价为参考价，以船司实时报价为准」）。

> 与旧规则的冲突必须一并解决：`AGENT_INSTRUCTIONS` 里有一条「数据列表由界面自动渲染成表格卡，
> 正文禁止再手写 Markdown 表格」——而运价结果卡已被设成静默（中间产物不上屏）。
> 两条并存的结果就是模型自己拼一张错格式的表。运价类要显式**以本规范为准**：正文必须带工具给的表。

## 4. 数字纪律（沿用既有，再钉一遍）

- 条数只认 `total`（真总数），展示行数只认 `count`/数组长度；`complete:false` 必须说「已显示前 N 条，共 M 条」；
- 价格、有效期、船司、柜型只能出自本次返回；缺就写「未注明」或 `/`，不许推算或按常识补；
- 同一轮两次数字打架 → 以最后一次完整查询为准并明说更正，不许静默改口。

## 6. 验收

- 单测：L1 命中具体港时不混入航线级行；L1 为零才走 L2 且表里标注航线级；`userTable` 表头 12 列逐字锁死；
  `customerTable` 只在 `forCustomer:true` 时非空；空结果不写缓存；数字口径（total vs count）不串。
- 手动：分别问「Santos 的价」「宁波到桑托斯 40HQ」「南美东现在什么价」「地东的价格」——
  每次都必须是「一句结论 + 12 列表格（+舱位表）」，不许出现散文罗列或第二张自拼表。

## 9. 2026-09-09 会话实测后的三点补充

1. **精简视图 `priceDigest`**：12 列工作表对「只想看最低价」太宽，模型会自己缩成 6 列并顺手把内部备注带出去。
   现在服务端直接给一份 6 列精简表（船司/起运港/目的港/价格/有效期/备注），备注走 `customerRemarkEn` 同一套判丢，
   内部黑话（成本价/批价/可减多少）不进来；notice 改为「要摘要就贴 priceDigest，仍不许自己另拼表或改数字」。
2. **「给客户的价格表」防呆**：用户原话（`ctx.userText`）里出现 给客户/发给客户/客户价格表/报价表 而本次调用没带
   `forCustomer=true` → 返回里下指令要求带 forCustomer 重查，绝不允许把中文工作表改列后当对外表贴出去（事故级泄漏）。
3. **返回体瘦身**：`limit` 硬钳 1..50（实测模型传 200 → 单轮 21 万 token）；`quotes` 只留决策字段且最多 20 条；
   舱位只回 `spaceTable` 文本 + `spaceCount`，不再重复给明细数组。
