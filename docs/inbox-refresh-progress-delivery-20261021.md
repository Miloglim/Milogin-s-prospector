# 收件箱刷新进度与 IMAP 续抓

## 目标

让用户能从刷新弹窗判断后台正在连接、查找、扫描、校准还是收尾，并明确本轮看了多少、新增多少、还有多少留到下一轮；同时修复 IMAP 超过 500 封时重复扫描首批的问题。

## 已实现

- `src/shared/inbox.ts` 定义 `InboxFetchProgress` 和阶段常量，保留原 `inbox:fetchProgress` 通道。
- IMAP/POP3 每扫描 5 封推送一次真实批次进度；POP3 不再一直停在“连接服务器”。
- IMAP 使用 `imap_fetch_uid_validity` 与 `imap_fetch_last_uid` 续抓，每轮最多 500 封，成功后推进游标；UIDVALIDITY 变化时安全重扫。
- 手动刷新等待退信补匹配和 Sent 探测结束后再标记完成；正文缓存仍异步限速预取，不阻塞刷新。
- 进度弹窗按账号展示阶段；扫描阶段展示 `已扫描/本轮总数`、新增数和待下轮数量，并移除与真实进度脱钩的流动条动画。
- 弹窗可点关闭或“转入后台”，只隐藏界面，不取消后台抓取；抓取未结束时刷新按钮显示“后台拉取中”，点击可重新打开进度。
- IMAP 账号本地入站邮件少于 200 封时，额外检查服务器最新 200 个 UID 并把缺失部分并入本轮扫描；已有邮件仍按 Message-ID 去重。该补拉与常规 UID 水位共用 500 封单轮上限。
- 最近 200 封和 500 封单轮上限属于内部执行参数，进度弹窗只显示已扫描与新增数量，不把批次上限暴露成邮箱总量。

## 边界

- IMAP 候选窗口仍为实际 6 天（5 天加 1 天时区缓冲），不是邮箱全历史。
- 单轮 500 封是保护上限；剩余量会在下次刷新继续，不在一次操作中无限扫完。
- POP3 继续只检查最新 40 个序号，没有持久化游标。
- 不使用真实邮箱验证本轮网络抓取；协议行为由共享分批测试、服务测试和渲染事件测试覆盖。
