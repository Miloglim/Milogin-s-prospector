# 客户看板关注规则（第一阶段）

## 范围

本阶段只调整客户看板的准入与原因标签，解决批量初次开发后大量联系人进入看板的问题。邮件存储、收件箱、发送中心、任务创建、依赖和中心数据库结构均不变。

看板按联系人展示，但待办和业务阶段属于客户。为避免同一客户的其他联系人被一起带上看板，规则必须落到具体联系人。

## 页面职责

| 页面 | 负责的信息 |
|---|---|
| 联系人表 | 全量已授权联系人、搜索、分组和常规维护 |
| 收件箱 | 来信、退信、自动回复、邮件分析和邮件待办 |
| 发送中心 | 已接受/已发送、批量发送批次、退信和自动回复等执行结果 |
| 客户看板 | 需要人与人继续处理的联系人：真实回复、开放待办、报价/试单/合作阶段 |

## 准入表

| 事实 | 看板准入 | 原因 |
|---|---:|---|
| `touchStatus=replied` | 是，仅该联系人 | `reply` |
| 开放待办有 `source_contact_id` | 是，仅来源联系人 | `task` |
| 开放待办无 `source_contact_id` | 是，仅最低未删联系人 ID | `task` |
| `relationship_stage in ('quoting','trial','cooperating')` | 是，仅最低未删联系人 ID | `stage` |
| `contacted`、`bounced`、`autoreply` | 否，单独不进入 | 无 |
| `cold`、`reaching` 且无回复/待办/业务阶段 | 否 | 无 |

优先级为 `reply` → `task` → `stage`。中心返回的 `attentionReason` 已经是联系人级结果，离线镜像优先信任；旧缓存没有原因时只派生本联系人回复和主联系人业务阶段。

## 标准参考案例

1. 导入 1000 个联系人并发送 1000 封开发信，`contacted` 为 0 条看板记录。
2. 退信、自动回复各自为 0 条看板记录。
3. 联系人真实回复后，只显示这个联系人，标签为“客户回复”。
4. 同一客户有三个联系人、一个来源联系人为 B 的开放待办，只显示 B，标签为“已约跟进”。
5. 同一待办没有来源联系人时，只显示最低未删联系人 A。
6. 客户阶段为 `quoting/trial/cooperating` 时，只显示最低未删联系人，标签为“业务阶段”。

## 核心规则

```sql
ct.crm_touch_status = 'replied'
OR EXISTS (
  SELECT 1
  FROM crm_followup_tasks ft
  WHERE ft.customer_id = c.customer_id
    AND ft.status = 'open'
    AND (
      (ft.source_contact_id IS NOT NULL AND ft.source_contact_id = ct.id)
      OR (ft.source_contact_id IS NULL AND ct.id = <lowest non-deleted contact id>)
    )
)
OR (
  ct.id = <lowest non-deleted contact id>
  AND c.relationship_stage IN ('quoting','trial','cooperating')
)
```

```ts
customerBoardAttentionReason({
  touchStatus,
  openTaskMatchesContact,
  relationshipStage,
  isPrimaryContact,
});
```

## 闭环冒烟测试

1. `centerContactPath` 生成 `attentionOnly=true`，HTTP 路由必须把它解析成布尔值，不能作为字符串交给契约校验。
2. 在隔离 PostgreSQL 事务中建立同一客户三个联系人，分别验证来源联系人待办、无来源待办、业务阶段都只返回一条。
3. 用 1000 条 `contacted` 联系人加载客户看板，确认看板请求带 `attentionOnly=true`，页面没有联系人条目。
4. 加入 `replied`、开放待办、`quoting` 三类联系人，确认分别出现“客户回复”“已约跟进”“业务阶段”，且退信、自动回复未出现。
5. 断开中心，重复第 4 步的离线镜像验证；旧缓存缺少原因时，确认只按回复和主联系人阶段兜底。
6. 打开联系人表、收件箱、发送中心，确认原有邮件和发送记录仍可见，没有被本阶段规则删除或改写。

## 发布与回滚

- 发布顺序：中心接口先支持 `attentionOnly` 与 `attentionReason`，桌面端随后切换看板查询。旧桌面端的 `followupOnly` 仍由服务端兼容。
- 回滚应用：桌面端改回 `followupOnly` 或旧版本即可；中心仅多返回兼容字段，不写数据。
- 本阶段没有 DDL、迁移或数据回填，不需要回滚数据库。
- 发布前必须完成隔离测试、构建和知识库同步检查；未在真实中心执行迁移验收。

## 第二阶段：我的工作台

普通销售的“我的”工作台复用同一条关注准入。`personal` 与 `assigned` 两个联系人请求都带 `attentionOnly=true`，前端不再按 `touchStatus` 二次筛选，因此未触达但属于业务阶段的主联系人、以及由开放待办准入的联系人都不会被丢掉。

| 工作台区域 | 规则 |
|---|---|
| 左侧筛选 | `全部关注 / 客户回复 / 客户待办 / 业务阶段` |
| 顶部指标 | 按 `attentionReason` 统计 reply/task/stage，另显示当前全部关注数 |
| 行动分组 | reply/task 进入“现在要做”，stage 进入“推进阶段” |
| 行内下一步 | reply=回复客户，task=处理待办，stage=推进阶段 |
| 旧缓存兜底 | 有原因就显示原因；缺少原因时保留原有动作文案，不恢复 `contacted/bounced/autoreply` 筛选 |

“总待办”仍显示全部开放待办；“客户待办”仍按当前选中的客户过滤。该阶段没有新增依赖、IPC、数据库结构、发送中心或收件箱逻辑。

## 第三阶段：最早待办到期时间

关注联系人新增派生字段 `attentionDueAt`，只取与当前联系人匹配的开放待办最早 `due_at`：有 `source_contact_id` 时必须等于当前联系人；来源为空时只取最低未删主联系人。其他客户或其他联系人任务不会影响这个时间。

| 优先级 | 本地日历判断 | 示例标签 |
|---:|---|---|
| 1 | 到期日早于本地今天 | `逾期 2 天` |
| 2 | 客户真实回复且未逾期 | 原因标签“客户回复” |
| 3 | 到期日是本地今天 | `今天到期` |
| 4 | 待办在未来，或待办暂无到期时间 | `周四跟进` / `11/28 跟进` |
| 5 | 报价/试单/合作阶段 | 原因标签“业务阶段” |

看板在现有阶段分组内按该优先级排序，再按原最近跟进时间排序；工作台使用同一优先级分组和排序。筛选仍只保留 `全部关注 / 客户回复 / 客户待办 / 业务阶段`，到期紧迫度是派生排序信息，不是新的持久状态或筛选。

离线镜像直接保留中心快照里的 `attentionDueAt`；旧缓存没有该字段时继续工作。本阶段没有 DDL、迁移、新依赖或正式中心写入。

## 第四阶段：发送任务结果进入收件箱

发送中心只负责看清任务、批次和结果，不复制邮件列表。任务卡片上的“已收到 / 退信 / 自动回复”与详情里的“查看任务邮件”统一跳到现有收件箱，并携带 `campaign` 和可选 `campaignStatus`；收件箱继续负责邮件正文、回复、退信、自动回复和后续处理。

收件箱复用现有 `send:campaignDetail` 读取任务目标，不新增 IPC、数据库字段或邮件副本。当前已加载邮件按以下任一事实归到任务：

1. `matchedContactId` 命中任务目标联系人。
2. 发件邮箱命中任务目标邮箱。
3. 邮件的中心联系人引用命中任务目标。
4. 指定结果时，再按 `sent / replied / bounce / autoreply` 分类限定。

顶部任务条显示任务名和当前结果，可一键清除筛选并回到普通收件箱。发送任务与收件箱之间没有自动写入或状态同步；同一批邮件仍只有收件箱这一份事实。

标准案例：任务 A 的目标联系人只有 `buyer@campaign.invalid`，收件箱同时有该联系人的回复、退信和另一位联系人的回复。进入“已收到”时只显示任务 A 的回复；清除后三封邮件都恢复。任务目标没有对应邮件时显示空结果，不能拿其他联系人的同类邮件补足。

验证：渲染测试覆盖结果链接和任务筛选；隔离 Electron 使用合成中心与本机 SQLite 确认筛选、清除恢复、1440/824 无横向溢出、页面错误 0。本阶段没有新增依赖、DDL、迁移、正式中心写入或真实邮件访问。

## 历史范围边界（前三个阶段）

- 不实现发送中心的新分组、筛选或状态机。
- 不改变收件箱和邮件分析规则。
- 不新增表、列、索引或任务字段。
- 不做前端分页后过滤；看板使用服务端和离线镜像返回的完整已授权关注结果。
- 不声称真实中心已迁移或正式发布已完成。
